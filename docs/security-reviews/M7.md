# Security review — M7 New-place mode and stats

Date: 14 November 2026. Scope: the lunch history in D1, new-place mode in
the room, `GET /api/stats` and the "Eerdere lunches" page, the admin
"Lunches" tab.

## What changed

- Migration 0003: `lunch_history` (restaurant name, food types, time, number
  of respins, whether new-place mode was on). No participant data.
- The room writes one row when it reaches its final result, keyed by a random
  per-room reference (`INSERT OR IGNORE`), so a repeated alarm cannot write
  twice. Best effort: a D1 error never breaks the room.
- New rooms receive the set of restaurant names the team has ended up at.
  Each restaurant in the room state carries `visited`.
- Host-only `set_new_place {on}` (lobby only, strict schema): restaurants with
  `visited: false` get `LIMITS.newPlaceSlices` (1) extra slice. The server
  applies it when building the reel; the list shows the same odds via the
  shared `restaurantSlices`.
- `GET /api/stats` (team session): total, top 10, latest 20.
- Admin: list history (paged), delete one entry, delete all; each audited and
  behind the same Access, Origin and header checks as every admin change.

- [x] Threat model updated to v8 (T13, I5, asset "Lunch history")
- [x] New message and endpoints: host and phase checks; strict schemas (`on` must be a boolean);
      team session for stats; Access + CSRF checks for admin; ids validated (`^[1-9][0-9]{0,15}$`)
- [x] Tests: visited marking (also for restaurants added in the room); mode host-only, lobby-only,

      admin Lunches tab

## Findings

| #   | Finding                                                                                 | Severity | Status                                                                                                                 |
| --- | --------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| F1  | A repeated alarm could record the same lunch twice                                      | Low      | Fixed: unique random per-room reference with `INSERT OR IGNORE`; tested                                                |
| F2  | Anyone with the team key can see where the team ate                                     | Info     | Accepted: that is the feature; no names of people are stored                                                           |
| F3  | A participant can steer "visited" by adding a restaurant under an existing name variant | Info     | Accepted: names are matched case-insensitively; a variant only costs that restaurant its bonus, the host can remove it |
| F4  | Test rooms end up in the statistics                                                     | Info     | Accepted: admins can delete single entries or everything                                                               |
| F5  | The "nieuw" tag was cut off by long names on narrow phones                              | Info     | Fixed: the tag sits on the food-type line                                                                              |

## Residual risk

Low. No client can write to the history; the mode only changes slices the
server itself computes, and only before the lever is pulled.
