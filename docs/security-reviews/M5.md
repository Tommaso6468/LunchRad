# Security review — M5 Admin and presets

Date: 14 November 2026. Scope: D1 schema and migrations, the admin API under
`/admin/api`, Cloudflare Access verification, preset choice at room
creation, the open-room registry, team-key rotation, the admin screens.

## What changed

- D1: restaurants, presets (one default), preset contents, audit log, open
  rooms, admin-set team key. The pre-M5 list is migrated into the default
  list "Kantoor". Rooms copy their list at creation.
- `/admin` (lazy-loaded screens) and `/admin/api/*`, behind Cloudflare Access.
  The Worker verifies the `Cf-Access-Jwt-Assertion` token itself: RS256 only,
  key from the team's JWKS (cached 10 min, refetch for a new key id at most
  once a minute), issuer, audience, `exp`/`nbf`/`iat` with 60 s skew, and the
  email against `ADMIN_EMAILS`. Missing or malformed config: 503.
- Admin changes require the exact Origin, `X-Lunchrad-Admin: 1` and JSON;
  every change and its audit row go in one D1 batch.
- Admin can close any open room (`closed_by_admin`) and rotate the team key:
  server-generated (4×5 characters, about 100 bits), shown once, only
  HMAC(SESSION_SECRET) stored, never logged; all team sessions become invalid.
- Hosts pick a list when creating a room (`GET /api/presets`, team session).
- The restaurant list shows each chance as a percentage (PR #18).

## Findings

| #   | Finding                                                                                      | Severity | Status                                                                                                                                 |
| --- | -------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | Access authenticates with a cookie, so a plain cross-site POST would carry it                | Medium   | Fixed: exact Origin, custom header and JSON required for every change; tested                                                          |
| F2  | Trusting the Access header's presence would let anyone who reaches the Worker another way in | High     | Fixed: full signature and claim checks in the Worker; the header alone is never enough                                                 |
| F3  | After a team-key rotation, other Worker instances accept old sessions for up to 30 s (cache) | Low      | Accepted: bounded and documented; the instance that rotated clears its cache at once                                                   |
| F4  | The admin's email account is a single point of failure (one-time PIN)                        | Medium   | Accepted, owner action: strong 2FA on that mailbox (setup.md part 5)                                                                   |
| F5  | Open-room registry can keep rows of rooms that closed without removing themselves            | Info     | Accepted: rows expire with the room's 30-minute limit and are pruned on every list; closing an already closed room answers 404         |
| F7  | An admin-chosen team key is weaker than a generated one                                      | Low      | Accepted with limits: 12–64 characters, at least 6 distinct, not digits only; the session endpoint stays at 10 tries per minute per IP |
| F6  | Admin emails and restaurant names are stored in the audit log indefinitely                   | Low      | Accepted for now (minimal personal data: the admin's own address); retention to be set in M7                                           |

## Residual risk

Low, provided Access is configured as in setup.md and the admin mailbox is
protected. Even with Access misconfigured (for example the path not
covered), the admin API stays closed: it needs a valid token signed by the
team's Access keys for the configured audience and an allowed email.
